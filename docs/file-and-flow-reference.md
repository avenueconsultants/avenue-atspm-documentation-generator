# How this project runs: a plain-language file and path guide

**Start here.** There are two repositories in a normal run:

- The **consumer** is the application being documented, such as Data Downloader.
  It owns the C# source, a small root `documentation.json` file,
  and the finished files in `docs/autogenerated/`.
- This **generator** repository owns the scanning code, page templates, site
  builder and shared GitHub workflows. A consumer points at a particular
  reviewed commit of this repository. The generator does not need a separate
  copy of every consumer's source in Git.

If you want the big picture, read through **One change, from source to PR**,
**Where the paths point**, and **Which program calls which file**. The rest is
an alphabetical-by-folder reference for every file in this working tree.

This guide includes local, uncommitted work on
`feature/generic-documentation`. Example consumer workflows reference generator
`@main`; they cannot run until these shared workflows are merged there. During
branch-only development, replace `@main` with a pushed generator branch or
full commit SHA. The Pages example publishes only after the
consumer's reviewed generated files are committed and its Pages settings are
configured.

## A few words used below

| Word | Plain meaning |
| --- | --- |
| **Map** | The consumer's JSON instructions: which C# folders to scan, what pages to make, and how to name them. |
| **Source root** | The top directory of the consumer checkout. All `sourcePaths` in the map start here. |
| **Container** | One documentation page in the map. A container can represent a service, tool, or component. It is not a Docker container. |
| **Snapshot** | JSON describing the last documented configuration. The next run compares against it to explain changes. |
| **Manifest** | A list of files the generator owns. It stops the generator from replacing a person's handwritten files. |
| **Staging** | A temporary directory where new output is built and checked before it replaces the old output. |
| **Caller workflow** | The short GitHub Actions YAML file copied into a consumer; it starts a shared workflow in this generator repository. |
| **Preview artifact** | A downloadable result attached to a GitHub Actions run; it is for review, not a published website. |

## One change, from source to PR

Imagine a developer adds a `RetryCount` property to Data Downloader's
`DownloaderConfiguration` C# class. They push that source change to its
`documentation-integration` branch. Here is what happens **after its caller
workflow is installed and pinned**:

1. GitHub reads **consumer** `.github/workflows/update-documentation.yml`.
   Its push trigger matches the branch. It calls this repository's
   `.github/workflows/documentation-pr.yml` at the pinned commit. A manual run
   can also start the caller once GitHub exposes it on the default branch.
2. The shared workflow makes three separate checkouts. `_generator/` contains
   this tool. `_source/` contains the exact consumer commit that triggered the
   push. `_target/` contains the consumer branch that would receive the docs PR.
   These names exist only inside that Actions job; the ignored `_source/` in a
   developer's local generator checkout is a different directory.
3. `scripts/prepare_documentation_pr.py` reads **consumer**
   `_source/documentation.json`. In the Downloader example,
   its `sourcePaths` contains `atspm-data-downloader`. That means the scanner
   reads C# beneath `_source/atspm-data-downloader/`. The map's
   `logMessages.sourcePaths` separately points at its logging folder.
4. The script calls the .NET executable. `Program.cs` reads the map, scans the
   selected C# files, and finds `RetryCount` in the registered section. The
   Downloader's `autoDiscover` page already owns that section, so nobody has
   to list the new property in JSON. The generator reads the old
   `_target/docs/autogenerated/configuration-snapshot.json` to identify what
   changed. If there is a new *section* with no automatic page, a person must
   choose its page; the program does not guess service ownership.
5. New files are written in staging: the Downloader page now has a `RetryCount`
   row, its example files include the setting, and
   `configuration-changes.md` explains the change. The generator also writes a
   new snapshot and ownership manifest. It does **not** edit the application's
   C# code or its real deployment settings.
6. MkDocs builds the staged Markdown into an HTML site using `mkdocs.yml`,
   `scripts/site_configuration.py`, and `overrides/`. If scanning, ownership
   checks, or the strict site build fails, the workflow stops before PR
   creation. On success it uploads a `documentation-preview` artifact.
7. `prepare_documentation_pr.py` compares the new files with `_target`.
   Timestamp-only and source-revision-only differences are ignored for PR
   purposes. If `create-pr: true` and the content meaningfully changed, the
   workflow copies the generated files into `_target` and opens or updates a
   ready-for-review PR. Its body names changed settings and environment
   variables. With a consumer CODEOWNERS rule, the cloud team is requested
   for review.
   A person reviews and merges that PR; the workflow never merges it.
8. An optional, separate Pages caller may then read the *committed* generated
   files, validate them, and upload a site preview. It deploys to GitHub Pages
   only when the consumer's Pages caller sets `publish: true`, as the example
   caller does after reviewed docs are committed.

That is the reason the consumer commits its generated files: they are the
reviewable result, the previous comparison baseline, and the input for any
later Pages preview.

## Where the paths point

For this example, assume the consumer checkout is `C:\work\downloader` and this
generator checkout is `C:\work\atspm-documentation-generator`:

| Path or setting | Resolved place | Who reads or writes it |
| --- | --- | --- |
| `--source-root C:\work\downloader` | Consumer checkout root | Scanners use it as the starting point. |
| `documentation.json` | `C:\work\downloader\documentation.json` | Developer owns it; setup commands and generator read it. |
| `sourcePaths: ["atspm-data-downloader"]` | `C:\work\downloader\atspm-data-downloader\` | C# configuration scanner reads files below it. |
| `logMessages.sourcePaths` | Paths below `C:\work\downloader\` | Optional log scanner reads these C# files. |
| `--output-root C:\work\downloader\docs\autogenerated` | Consumer generated-docs directory | Generator writes; later runs read its snapshot. |
| `config/container-config-map.json` | Inside the generator checkout | Legacy bundled ATSPM default when no consumer map is supplied to `action.yml`. |
| `_source/` in this generator checkout | Local ignored consumer clones | Developers and generator integration tests use them; they are not committed. |
| `_generated/` in this generator checkout | Local ignored output previews | Developers review them; they are not committed. |
| `_generator/`, `_source/`, `_target/` in Actions | Three temporary checkouts in one job | Shared PR and Pages workflows create them as needed. |

The map's relative paths are relative to the **consumer source root**, not to
the map file and not to this generator repository. The output directory is a
separate dedicated directory. A consumer should commit its generated
`docs/autogenerated/` files; this generator's `.gitignore` does not hide files
in another repository.

### What gets written to the consumer output directory

| File in `docs/autogenerated/` | Why it exists |
| --- | --- |
| `index.md` | Home page linking to configured pages and reports. |
| `<slug>.md` | One configuration reference for each container/page in the map. |
| `<slug>.example.json` and `<slug>.env.example` | Safe copyable configuration examples for that page. |
| `configuration-templates.md` | Explains the examples and their source revision. |
| `configuration-snapshot.json` | Machine-readable comparison baseline; keep it in Git. |
| `configuration-changes.md` | Human-readable explanation of modeled configuration differences. |
| `log-messages.md` | Log reference, only when logging is enabled in the map. |
| `.atspm-docs-generator.json` | Hidden ownership manifest; also keep it in Git. |

The HTML site is built from those Markdown files for validation or a preview.
It is not the authoritative consumer output. An ordinary local MkDocs build
uses `site/build/` here; workflows build in a temporary job directory.

## Which program calls which file

The word **called** applies to commands, functions and workflows. C# source
files are compiled together into one executable; most are not launched as
separate programs. JSON maps and templates are **read**, not called. Tests run
only when a developer or CI invokes a test command.

| Starting action | Next files/functions | What it does |
| --- | --- | --- |
| `dotnet ... init` | `Program.cs` → `SetupCommands.cs` → discovery/map helpers | Writes a starter consumer map if one does not exist. |
| `dotnet ... check` | `Program.cs` → `SetupCommands.cs` → discovery/map/log analyzers | Checks coverage and references; writes nothing. |
| `dotnet ... sync` | `Program.cs` → `SetupCommands.cs` → discovery/map helpers | Shows proposed map additions; `--write` applies them. |
| `dotnet ... --workspace-root ...` | `Program.cs` → discovery/log analyzers → page/template/change generators → staged output | Reads source and prior snapshot; writes generated files. |
| Direct GitHub action | `action.yml` → `resolve-config-path.sh` → .NET executable → MkDocs | Generates and validates, without a PR. |
| Consumer documentation caller | Consumer YAML → `documentation-pr.yml` → `prepare_documentation_pr.py` → .NET/MkDocs | Uploads preview; opens a review PR when docs change. |
| Consumer Pages caller | Consumer YAML → `documentation-pages.yml` → `validate_publication.py` → MkDocs | Previews committed docs; may publish if enabled. |
| Generator CI | `.github/workflows/ci.yml` → .NET/Python tests and pinned checks | Tests this generator against fixtures/consumers. |

### Example 1: create and check a map locally

Run these in **PowerShell**. Change the two checkout paths to your own. This
example assumes `C:\work\sample-service\src\` contains the application's C#
files and that the map does not yet exist. `init` creates the JSON file;
`check` reads it and reports coverage. Neither command generates pages.

```powershell
$generator = 'C:\work\atspm-documentation-generator'
$consumer = 'C:\work\sample-service'
$dll = Join-Path $generator 'src\GenerateDocuments\bin\Release\net8.0\AtspmDocsGenerator.dll'

dotnet build (Join-Path $generator 'GenerateDocuments.sln') --configuration Release
dotnet $dll init --source-root $consumer --source-path src --product-name 'Sample Service'
dotnet $dll check --source-root $consumer
```

`init` creates `C:\work\sample-service\documentation.json`.
Open that file and check the scanned folders, page names and any suggested
unannotated configuration types. A new map made by `init` has one
`autoDiscover` page with slug `configuration`.

### Example 2: assign an unmapped section

Use `sync` when you have an **explicit** page map and `check` reports a new
section with no page. The first command is a preview; the second changes the
consumer's JSON file. Replace `configuration` with the destination page's
actual `slug`. An `autoDiscover` page already includes its new sections, so
the starter map above normally does not need this step.

```powershell
dotnet $dll sync --source-root $consumer --container configuration
dotnet $dll sync --source-root $consumer --container configuration --write
dotnet $dll check --source-root $consumer
```

Review the map diff after `--write`. The command adds assignments; it does not
edit C# source or generated pages.

### Example 3: generate files directly on your computer

This runs the same .NET generator without GitHub Actions. It reads the
consumer map, selected C# files and any prior snapshot in the output folder.
It writes the finished files to the consumer's `docs\autogenerated\` directory.
The revision and timestamp below come from the consumer checkout, so generated
source links point at the source being documented.

```powershell
$revision = git -C $consumer rev-parse HEAD
$commitTime = git -C $consumer show -s --format=%cI $revision

dotnet $dll `
  --workspace-root $consumer `
  --source-root $consumer `
  --output-root (Join-Path $consumer 'docs\autogenerated') `
  --map (Join-Path $consumer 'documentation.json') `
  --repository-url 'https://github.com/OWNER/sample-service' `
  --repository-ref $revision `
  --generated-at $commitTime
```

Replace `OWNER/sample-service` with the consumer's real GitHub repository.
The direct .NET command generates Markdown and examples; it does **not** run
MkDocs. For a local HTML check, install `requirements.txt` from this generator,
then set `DOCS_CONFIG` and `DOCS_DIR` and run MkDocs from the generator folder:

```powershell
python -m pip install --requirement (Join-Path $generator 'requirements.txt')
$env:DOCS_CONFIG = Join-Path $consumer 'documentation.json'
$env:DOCS_DIR = Join-Path $consumer 'docs\autogenerated'
Push-Location $generator
try { python -m mkdocs build --strict } finally { Pop-Location }
```

### Example 4: call the composite action directly

Put a workflow like this in the **consumer** at
`.github/workflows/generate-documentation.yml`. The composite action builds
the .NET executable, generates files and validates the site. The last step
uploads the generated files for review. It does **not** commit them or create a
PR. The example follows generator `main`; replace `@main` with a full
40-character commit SHA if the consumer must stay on one version.

```yaml
name: Generate documentation preview
on: workflow_dispatch
jobs:
  preview:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-dotnet@v5
        with:
          dotnet-version: 8.0.x
      - uses: actions/setup-python@v6
        with:
          python-version: '3.11'
      - uses: avenueconsultants/avenue-atspm-documentation-generator@main
        with:
          source-root: .
          config-file: documentation.json
          output-root: docs/autogenerated
          repository-url: https://github.com/${{ github.repository }}
          repository-ref: ${{ github.sha }}
          validate-site: 'true'
      - uses: actions/upload-artifact@v4
        with:
          name: generated-documentation
          path: docs/autogenerated/
          include-hidden-files: true
```

### Example 5: call the shared documentation PR workflow

This is the usual consumer setup. Put it at **consumer**
`.github/workflows/update-documentation.yml`. This example targets a branch
named `documentation-integration`; change **all three** branch references for
your repository. The example uses generator `main`; replace its one `@main`
with a full commit SHA to pin a version. On a matching source push it uploads a
`documentation-preview` artifact and opens a review PR when docs change.
The cloud team's review request comes from a real `.github/CODEOWNERS` rule
on the PR target branch; the PR body shows modeled configuration changes.

```yaml
name: Update generated documentation
on:
  workflow_dispatch:
  push:
    branches: [documentation-integration]
    paths-ignore:
      - 'docs/autogenerated/**'
permissions:
  contents: write
  pull-requests: write
jobs:
  documentation:
    uses: avenueconsultants/avenue-atspm-documentation-generator/.github/workflows/documentation-pr.yml@main
    with:
      source-branch: documentation-integration
      target-branch: documentation-integration
      create-pr: true
```

GitHub normally shows the manual Run workflow button only after the caller
exists on the repository's default branch. During branch-only development,
push to the configured development branch to test it. The PR base above is
`documentation-integration`; nothing targets `main` automatically.

### Example 6: preview committed files with the Pages workflow

After a docs PR is reviewed and merged into the development branch, put the
optional caller below at **consumer**
`.github/workflows/publish-documentation-pages.yml`. It follows generator
`main` unless you change its one ref to a full commit SHA. This validates the committed map, manifest, snapshot and
generated files, then uploads a `documentation-pages-preview` artifact and
publishes the site. Configure Pages and its `github-pages` environment in the
consumer before using this caller.

```yaml
name: Publish reviewed documentation site
on:
  workflow_dispatch:
  push:
    branches: [documentation-integration]
    paths:
      - 'docs/autogenerated/**'
permissions:
  contents: read
  pages: write
  id-token: write
jobs:
  pages:
    uses: avenueconsultants/avenue-atspm-documentation-generator/.github/workflows/documentation-pages.yml@main
    with:
      docs-branch: documentation-integration
      publish: true
```

### Example 7: run this generator's checks

Run these from the **generator** repository after changing generator code,
scripts or workflows. `.github/workflows/ci.yml` runs the corresponding checks
on generator PRs and pushes to `main`. Its pinned integration checks need the
consumer checkouts described in that workflow.

```powershell
dotnet test GenerateDocuments.sln --configuration Release
python -m unittest discover -s scripts -p 'test_*.py'
python scripts/validate_repository.py
```

The direct executable requires `--workspace-root`, `--source-root`,
`--output-root`, `--map`, `--repository-url`, `--repository-ref`, and
`--generated-at`. `action.yml` supplies these from its inputs and the source
commit. Output must be inside the workspace. Source links use the supplied
repository URL and ref. The scanner does not fetch Git history, run the
consumer application, or read live deployment values.

## If you need to change something

| What you want | Start with | Why |
| --- | --- | --- |
| Add a new repository | Consumer `documentation.json`, then a copy of `integration/update-documentation.yml` | The consumer supplies folders and pages; the shared workflow supplies the machinery. |
| Include a new C# folder | Consumer map `sourcePaths` or `logMessages.sourcePaths` | Only registered folders are scanned. |
| Put a new section on a particular page | Consumer map `containers`, or `sync --container <slug>` | Explicit ownership is a human choice; `autoDiscover` is the simple alternative. |
| Improve a setting's description | C# XML comment or map `propertyDescriptions` | These become text in the generated reference. |
| Change a safe example value | Consumer map `examples` | The generator uses placeholders and approved overrides in templates. |
| Diagnose a missing setting | Run `check`; then inspect `ConfigurationDiscovery.cs` and `ConfigurationSourceAnalyzer.cs` | The source may be outside registered roots, unannotated, excluded, or unsupported. |
| Diagnose missing logs | Map `logMessages`, then `LogMessageSourceAnalyzer.cs` | Logging is optional and scans separate folders. |
| Change page text or layout | `MarkdownDocumentationGenerator.cs`, `LogMessageDocumentationGenerator.cs`, or `overrides/main.html` | C# renders Markdown; the override affects the HTML site. |
| Change comparison behavior | `ConfigurationChangeGenerator.cs` and `ConfigurationSnapshot.cs` | These decide which differences are recorded. |
| Change PR behavior | `.github/workflows/documentation-pr.yml` and `scripts/prepare_documentation_pr.py` | The workflow handles GitHub steps; the script prepares and compares files. |
| Change Pages behavior | `.github/workflows/documentation-pages.yml` and `scripts/validate_publication.py` | They validate committed output before preview or deployment. |

The individual file descriptions below explain each piece in more detail. Most
consumer changes require editing its map and source comments, not this
generator's C# code.

## Root files

### `.gitignore`
Git reads this during status/add operations. It excludes .NET build output,
IDE state, Python bytecode, local consumer checkouts and preview directories.
It does **not** apply to a different consumer repository; that repository must
decide whether its own `docs/autogenerated/` is tracked (it should be).

### `.gitattributes`
Git uses this when adding/checking out files. It fixes LF line endings for
vendored JavaScript, baseline snapshots and shell scripts so checksum and
snapshot comparisons remain stable across operating systems.

### `GenerateDocuments.sln`
`dotnet build` and `dotnet test` use this solution to include the generator and
its test project. GitHub CI also tests the solution. It is not read at runtime.

### `LICENSE`
The repository license. It is read by people and repository tooling, not the
generator process. Third-party browser libraries have separate licenses below.

### `README.md`
The entry point for developers adding a consumer: setup, commands, workflow
pins, outputs and known limits. GitHub displays it at the repository root.

### `requirements.txt`
Pip installs the Python packages needed for MkDocs site builds and validation.
The composite action, shared workflows and local site commands use it; the C#
analyzer itself does not.

### `action.yml`
The reusable **composite action** used for direct generation. It resolves
`source-root`, `output-root` and `config-file`, obtains the source commit time,
builds `src/GenerateDocuments`, runs its DLL, and optionally builds the site
with `mkdocs.yml`. It generates files but never commits or opens a PR. An empty
`config-file` selects `config/container-config-map.json` for legacy ATSPM use.

### `mkdocs.yml`
MkDocs reads this during strict site validation or Pages builds. `DOCS_DIR`
points at generated Markdown, `DOCS_CONFIG` at the map, and
`DOCS_REPOSITORY_URL` at the consumer source repository. It loads
`scripts/site_configuration.py`, uses `overrides/`, and normally builds to
`site/build/`; workflows override the site destination with a temporary path.

## Configuration files

### `config/container-config-map.json`
The bundled ATSPM map used when the composite action receives an explicitly
empty `config-file` input.
It also supplies compatibility and baseline tests. A new consumer should put a
copy tailored to itself at **consumer** `documentation.json`
instead of changing this ATSPM default.

### `config/container-config-map.schema.json`
JSON Schema describing and validating map version 2, including source folders,
page mappings, logs, examples and site branding. Editors can use it for map
authoring; `DocumentationMapLoader.cs` performs runtime validation.

### `config/documentation.example.json`
Human-copyable explicit-page example. It is documentation input, not selected
automatically by a workflow. Copy and edit it in a consumer if page ownership
must be specified.

### `config/documentation.auto.example.json`
Human-copyable `autoDiscover` example for a small consumer. It is not loaded
unless explicitly copied or passed as `--map`.

## C# generator (`src/GenerateDocuments`)

### `GenerateDocuments.csproj`
Defines the .NET 8 executable and Roslyn dependency. `dotnet build`, tests and
the action build it; output is under `bin/Release/net8.0/` (ignored by Git).

### `AssemblyInfo.cs`
Assembly metadata for test access to internal helpers. The compiler reads it;
the generator has no separate runtime call to this file.

### `Program.cs`
Executable entry point. Routes `init/check/sync` to setup, or loads the map,
checks output ownership, loads the previous snapshot, discovers C# sections and
logs, and writes all outputs through a staged transaction. It reports unmapped
sections and returns a nonzero code on supported validation or I/O errors.

### `CliOptions.cs`
Parses and validates generation options: existing paths, HTTP(S) repository
URL, source ref and timestamp, and output containment within the workspace.
Called by `Program.cs` before any generation work.

### `SetupCommands.cs`
Implements `init`, `check` and `sync`. It scans consumer source and validates
map references/logs. `init` writes a new map only if absent; `check` never
writes; `sync` previews additions unless `--write` is given. Sync requires an
explicit destination page for unmapped sections and keeps writes in the source
repository.

### `DocumentationMap.cs`
Map data types, JSON loading and semantic validation. `Program.cs` and setup
commands call its loader; generation, templates, logs and site presentation
consume the resulting page, source-path, exclusion, example and branding data.

### `ConfigurationModels.cs`
In-memory records for discovered sections/properties and generation counts.
The analyzers produce these records; page, template and snapshot code consume
them. This file does not itself read or write a path.

### `ConfigurationDiscovery.cs`
Coordinates section analysis across map `sourcePaths`, explicit type
registrations, exclusions and automatic page assignments. Called by setup and
generation. It detects missing/stale references and returns unmapped sections
instead of guessing service ownership.

### `ConfigurationSourceAnalyzer.cs`
Uses Roslyn to parse consumer C# source and extract configuration sections,
properties, types, defaults, annotations, comments and source locations. It
reads files selected by `SourceFiles.cs`; it does not compile or run the
consumer application.

### `SourceFiles.cs`
Enumerates C# files beneath registered source folders, pruning generated,
dependency and test directories and skipping links. Configuration and log
analyzers use it; paths remain under the consumer root.

### `SourcePath.cs`
Resolves a configured relative source folder inside the consumer root. The
analyzers use it to reject traversal or missing folders before scanning.

### `PathSafety.cs`
Canonicalizes paths and checks containment. CLI and setup/output operations
use it so configured paths cannot escape their allowed root.

### `XmlDocumentationReader.cs`
Reads C# XML summary comments from syntax nodes. Configuration and log
analyzers call it to add source-authored descriptions to generated pages.

### `MappedSectionName.cs`
Normalizes mapped section names and derives environment-variable prefixes.
Reference, template and snapshot generation use it for named bindings.

### `MarkdownDocumentationGenerator.cs`
Renders `index.md` and one `<slug>.md` reference page per configured container.
It includes configuration rows, examples, source links, navigation and the
change-report/template links. Called inside `Program.cs`'s staging transaction.

### `DocumentationText.cs`
Shared Markdown escaping, code spans, timestamps and source URL helpers used
by page/log/report renderers. It does not open paths by itself.

### `LogMessageModels.cs`
In-memory records for structured and ordinary log messages and render counts.
The log analyzer produces them; the log page renderer consumes them.

### `LogMessageSourceAnalyzer.cs`
Scans map `logMessages.sourcePaths` for `LoggerMessage` declarations and,
when enabled, supported ordinary `ILogger` calls. It checks event IDs and
source locations. Called only when the map enables logs.

### `LogMessageDocumentationGenerator.cs`
Renders `log-messages.md` from analyzed logs, including event metadata and
source links. Called in the staged generation transaction when logs are enabled.

### `ConfigurationExampleTree.cs`
Builds nested JSON structures for a section name and its properties. The
template generator calls it; it has no independent command or disk path.

### `ConfigurationTemplateGenerator.cs`
Writes `configuration-templates.md` plus `<slug>.example.json` and
`<slug>.env.example` for each configured page. It uses safe placeholder values
and map example overrides, then writes to the staged output directory.

### `ConfigurationSnapshot.cs`
Data records/schema for `configuration-snapshot.json` and comparison entries.
The change generator serializes these models. No path is opened by this file.

### `ConfigurationChangeGenerator.cs`
Loads the prior output snapshot, captures the current source contract, compares
modeled settings and service mappings, then writes
`configuration-snapshot.json` and `configuration-changes.md` in staging. The
prior committed output is the comparison baseline; no deployment config is
read. A no-change run retains the last meaningful report.

### `GeneratedOutputPolicy.cs`
Checks the existing dedicated output directory and its ownership manifest
before replacement. It writes `.atspm-docs-generator.json` listing managed
files after generation. This prevents taking over handwritten output files.

### `OutputDirectoryTransaction.cs`
Stages a full generation and replaces the output only after successful writes.
`Program.cs` uses it to keep an existing output intact if generation fails.

## Python and shell scripts (`scripts`)

### `resolve-config-path.sh`
Called by `action.yml` before generation. An explicit map path resolves from
the consumer source root (or absolute path); an empty input resolves to the
bundled ATSPM map only with an explicitly empty `config-file`; a missing root
map fails.

### `test-config-path.sh`
Called by generator CI. Exercises the shell resolver's relative, absolute,
fallback and invalid-path cases; it does not generate documentation.

### `prepare_documentation_pr.py`
Called by the shared PR workflow after separate source/target checkouts. It
validates relative paths, checks/syncs the source map, generates and site-builds
in temporary space, compares output semantically with `_target`, writes a
review artifact and PR body, and stages approved files in `_target`. It does
not itself commit, push or call GitHub's PR API.

### `validate_publication.py`
Called by the shared Pages workflow before building the site. It checks that
the consumer map and complete generated output are committed, match the
manifest, and identify a valid source repository/revision. It writes a short
review record into the workflow's temporary directory.

### `site_configuration.py`
MkDocs hook loaded through `mkdocs.yml`. It reads `DOCS_CONFIG` and generated
docs, then sets site title/navigation/branding and checks links to pages. It
also supports the browser export controls in the theme override.

### `validate_repository.py`
Developer/CI consistency check for repository navigation, vendor assets and
configuration expectations. It reads repository files, reports failures and
does not generate consumer docs.

### `check_baseline.py`
CI integration check against a pinned ATSPM source checkout and the frozen
baseline files under `tests/baselines/atspm`. It generates in temporary space
and compares expected compatibility output; not part of consumer workflows.

### `check_data_downloader.py`
CI integration check for the pinned Data Downloader checkout. It verifies its
map, source coverage, generated pages, logs, repeatability and site build in
temporary space. Not run in the consumer's documentation workflow.

## GitHub repository automation (`.github`)

actions. GitHub reads it; the generator does not.

## What is expected to be committed

Commit the generator's source, maps/examples, workflows, scripts, tests,
fixtures, site assets and this documentation after review. Do not add ignored
`bin/`, `obj/`, `.vs/`, `_source/`, `_generated/`, Python bytecode or MkDocs
build output. In a consumer, **do** commit its map, caller workflow and
`docs/autogenerated/` generated files (including the hidden manifest and
snapshot). That committed output is what later PR comparisons and Pages
validation read.
