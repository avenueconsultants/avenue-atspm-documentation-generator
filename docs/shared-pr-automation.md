# Shared documentation PR automation (Part 6)

The reusable workflow `.github/workflows/documentation-pr.yml` owns setup,
discovery, generation, strict site validation, preview artifacts and review PRs.
Consumers keep their JSON map, generated files and a small caller workflow.
Nothing merges a PR or deploys a site. These changes are local until reviewed and
committed; consumer integration is handled in Parts 7–10.

## Install on a development branch

1. Create `documentation.json` using `init`, or migrate the
   existing map. Verify it with `check` (see [setup commands](discovery-and-setup.md)).
2. Copy `integration/update-documentation.yml` to the consumer's
   `.github/workflows/update-documentation.yml`. ATSPM has its own example using
   `Code-Documentations`. Retire conflicting older generators during integration.
3. The example calls `@main`. Once this shared workflow is reviewed and merged
   into the generator's `main`, the consumer follows its updates automatically.
   To freeze a consumer on one version, replace only `@main` in its `uses` line
   with a full generator commit SHA. During branch-only development, use a
   pushed generator branch or SHA because `main` does not contain this workflow yet.
   The reusable job checks out its own repository at the exact workflow SHA.
4. Set the push branch, `source-branch` and `target-branch` explicitly. The
   caller has `create-pr: true`. Preserve the generated-output ignore filter,
   and update it if you change `output-directory`.
5. Run a push or manual dispatch. Inspect the `documentation-preview` artifact
   and the proposed PR. Its body lists modeled configuration changes and
   environment names. Review and merge the PR only after checking whether
   deployment settings need to change. Put a real cloud-team owner in the
   consumer's `.github/CODEOWNERS` for the map and generated docs.

GitHub only exposes manual dispatch when the workflow exists on the repository's
default branch. During branch-only development, use a push to the configured
development branch. Do not merge solely to make the Run workflow button appear.

The caller grants `contents: write` and `pull-requests: write`. The repository's
Actions settings must allow GitHub Actions to create PRs. Organization policy can
restrict this setting. The generator repository must be accessible to the caller;
this first workflow targets the canonical public generator repository. No PAT is
required. With GitHub's default token, PR-triggered checks may require a maintainer
to approve their workflow runs; inspect the PR checks before review/merge. See
[GitHub token behavior](https://docs.github.com/en/actions/concepts/security/github_token)
and [reusable workflows](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows).

The workflow opens a ready-for-review PR so GitHub can request review from
owners of `documentation.json` and `docs/autogenerated/`. Copy
[`CODEOWNERS.example`](../integration/CODEOWNERS.example) into the consumer's
`.github/CODEOWNERS` and replace the placeholder team. GitHub does not
automatically request CODEOWNERS reviews for draft PRs; an already-open draft
must be marked ready for review. See [GitHub's code-owner guidance](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners).

## Information flow and safeguards

1. A push uses the exact triggering source commit; a manual run uses the current
   `source-branch`. Only push/manual events are accepted. Pushes from a different
   source branch and use of the reserved automation branches are rejected.
2. Separate checkouts hold the generator, consumer source and PR target. The
   target branch supplies the previous committed snapshot and generated files.
   Application commits from a different source branch never enter the PR.
3. Optional `sync-container` adds newly discovered sections to that explicitly
   selected page. Without it, `check` reports unmapped sections and fails.
   `autoDiscover` pages incorporate new sections without rewriting JSON. Sync
   preserves manual values but rewrites formatting/comments as documented in
   Part 4. A synced map must match the target's original map, preventing an
   overwrite of divergent manual edits between branches.
4. Generation happens in a temporary directory containing the prior output.
   Corrupt snapshots, unmanaged output, invalid mappings, duplicate log IDs and
   strict MkDocs failures stop the run before target files are changed or PR
   automation runs. Only successful builds produce validated preview artifacts.
5. Comparison ignores generated timestamps and the revision portion of dedicated
   source links. Committed files stay byte-for-byte identical if those are the
   only differences. Source path/line changes, prose, defaults, examples, logs,
   additions/removals and map changes still count. Snapshots retain the last
   meaningful configuration comparison, as described in Part 5.
6. A 14-day preview artifact is uploaded even when no PR is needed. Meaningful
   changes can create/update one review PR, on a deterministic automation branch
   per target branch/output directory. Only generated output and an optional
   synced map are committed. Consumer application code is never executed.

Before PR creation, remote source and target heads must still match the checked-out
revisions. A superseded run fails with a rerun instruction instead of proposing an
older snapshot. Concurrency serializes runs for each target/output combination.

The PR branch is owned by automation: correct the source branch/map rather than
editing that branch, because subsequent runs regenerate it. Updates return the PR
to review. If the target already contains the result, PR automation is skipped;
any obsolete open PR can be closed during review. No automatic branch deletion,
merge, Pages deployment or wiki update is included.

Push filters ignore documentation-only changes, automation never targets its own
branch, and semantic comparison makes remaining reruns no-ops. A synced-map merge
may cause one extra validation run; stable discovery/comparison prevents another
PR. Keep broad source coverage so new folders/types need no workflow edits.

Different source/target branches are supported; normally use the same development
branch so references describe the application under review. Changing the output
directory creates a separate automation identity: retire the old PR/output
deliberately. Use one caller per target/output combination.

## Inputs

| Input | Purpose / default |
| --- | --- |
| `source-branch` | Required consumer branch to scan |
| `target-branch` | Required PR base, with no implicit `main` |
| `config-file` | `documentation.json` |
| `output-directory` | `docs/autogenerated` |
| `sync-container` | Empty; optional page slug for additive map updates |
| `create-pr` | `true`; propose a review PR when files change |

Paths must be simple repository-relative names without hidden directories,
traversal, symlinks or globs. Output must be dedicated to generated files. A
consumer map is required; the legacy composite action still supports the bundled
ATSPM map for direct generation.

PR maintenance uses a pinned version of
[create-pull-request](https://github.com/peter-evans/create-pull-request).
Hosted GitHub execution and repository policy checks still require the first
consumer preview/integration run.

## Local verification

The Python suite exercises first generation, exact preservation on a no-op rerun,
real default changes, additive map sync, divergent-map refusal, corrupt snapshots,
unmanaged files and a simulated strict-site failure. It invokes the built CLI in
fresh processes and performs real strict MkDocs builds. This also caught and fixed
a serializer initialization bug in `sync --write` that in-process tests missed.

Part 6 validation passed repository consistency checks and actionlint for the
reusable workflow, CI and both caller templates. The test suites have since
expanded; run the current suites when reviewing changes.
No live PRs, consumer branch changes or publishing were performed.
