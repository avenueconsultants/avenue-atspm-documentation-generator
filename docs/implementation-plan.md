# Shared documentation generator implementation plan

All development stays on branches. No automatic merges or production publishing.
Finish and review the shared generator before changing consumer repositories again.
Parts 7–9 created isolated local consumer review material, but further consumer
integration and hosted activation wait until shared tooling is complete.
ATSPM development uses `Code-Documentations` in the Avenue development repository;
its eventual home is `opensourcetransportation/atspm`. Other consumers use dedicated
integration branches. Documentation PRs must target the appropriate development
branch until rollout is explicitly approved.

## Reviewable parts

1. **Baseline:** establish the generator branch, run current checks, capture pinned
   ATSPM output, and inspect existing workflows. See [baseline report](baseline.md).
2. **Consumer configuration (implemented locally):** accept
   `documentation.json`, validate configuration, and preserve
   the existing ATSPM map. See [Part 2 details](consumer-configuration.md).
3. **Generic presentation (implemented locally):** derive navigation from configuration,
   parameterize branding and exports, support multiple log folders and optional
   logging. See [Part 3 details](generic-presentation.md).
4. **Discovery and setup (implemented locally):** init/check/sync commands, automatic
   discovery, explicit type registration, exclusions, and preservation of custom
   mappings. See [Part 4 details](discovery-and-setup.md).
5. **Change reports (implemented locally):** structured snapshots compare additions,
   removals, defaults, types, enum options, required status, environment names and
   affected services. See [Part 5 details](configuration-change-reports.md).
6. **Shared PR automation (implemented locally):** configurable source/target branches,
   manual and push triggers, staged validation, preview artifacts, one updating
   review PR, and no loops or timestamp-only PRs. See [Part 6 details](shared-pr-automation.md).
7. **Data Downloader (integrated locally; hosted activation pending generator ref):**
   consumer map, development-branch workflow, saved docs and pinned integration
   checks. See [Part 7 details](data-downloader-integration.md).
8. **ATSPM (integrated locally; hosted activation pending generator ref):** preserved
   six service pages, migrated the map, and removed the conflicting legacy workflow
   in the proposed `Code-Documentations` changes. See [Part 8 details](atspm-integration.md).
9. **Speed Listener (integrated locally; hosted activation pending generator ref):**
   verified actual section bindings, listener/emitter coverage, numeric defaults
   and dependency provenance. See [Part 9 details](speed-listener-integration.md).
10. **Data Migration (generator work in progress):** register existing types,
    exclude derived state, improve descriptions and support ordinary static
    logging calls. External package and untyped configuration coverage remains.
    See [Part 10 details](data-migration-integration.md).
11. **Configuration templates (implemented locally):** downloadable
    JSON/environment examples with safe placeholders and revision information;
    never modify deployment settings. See [Part 11 details](configuration-templates.md).
12. **Pages (implemented locally, publication disabled):** build preview artifacts
    from reviewed committed documentation; provide a guarded GitHub Pages path
    for later activation. See [Part 12 details](pages-publication.md).
13. **Adoption guide (implemented locally):** README setup, flow, triggers,
    discovery, review, publishing, troubleshooting and examples for all four
    consumers. Data Migration's remaining Part 10 coverage is stated explicitly.

Each part includes appropriate checks and documentation. Substantial new gaps get
their own reviewable change. Command-line reference generation, release-specific
sites and optional wiki publishing follow the initial rollout.

## Consumer shape

```text
documentation.json
.github/workflows/update-documentation.yml
docs/autogenerated/...
```

The shared generator owns parsing, discovery, presentation, validation and PR
automation. Consumers own source comments and a small configuration file. New
properties should require no map changes; new sections can join automatic groups.
Ambiguous explicit service mappings must be reported instead of guessed. Proposed
map changes belong in the documentation PR and must preserve manual customization.

## Configuration visibility

Keep configuration references current and expose deployment-relevant differences
to cloud teams. Do not promise runtime deployment validation from source parsing.
Report unsupported or unmapped settings; handle dependency-provided definitions
explicitly with version/provenance information. Never infer secret values or invent
event IDs. Distinguish CLI requirements, runtime rules and property annotations.

## Completion criteria

Each consumer can generate from a development branch, open/update a documentation
PR against that branch, retain generated files in its own repository, and rerun
without unnecessary changes. Existing ATSPM presentation remains recognizable.
Published output must match reviewed files and identify its source revision.
